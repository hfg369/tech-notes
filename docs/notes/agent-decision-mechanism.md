# Agent 的决策机制：下一步做什么

> 这是一篇学习笔记，用订单数据问答场景解释概念。它不是生产系统设计，也不声称完成了某个 Agent 产品。

AI Agent 中的“决策机制”，可以先用一句话理解：**系统根据目标、当前状态、可用动作和限制，选择下一步行动。**

用户问“上个月销售额为什么下降”时，Agent 可能先确认“销售额”的口径，再查询指标、拆分渠道、检查退款，最后判断证据是否足够。每一次选择都是一次决策。

## 四个输入

| 输入 | 要回答的问题 | 订单分析例子 |
| --- | --- | --- |
| 目标 | 最终要完成什么？ | 解释上月净收入下降的主要变化 |
| 状态 | 已经知道和做过什么？ | 已确认按支付日期统计，查到总额下降 |
| 动作 | 现在可以做什么？ | 澄清、查询、计算、回答、转人工 |
| 约束 | 哪些事不能做？ | 只能读分析库，限制查询范围与执行次数 |

目标不等于动作清单。目标是“完成分析”，动作只是候选步骤；状态改变后，候选动作也会改变。

## 决策循环

```text
读取目标与当前状态
        ↓
选择一个候选动作
        ↓
由程序检查动作是否允许
        ↓
执行动作或向用户提问
        ↓
保存结果，更新状态
        ↓
满足完成条件就结束，否则继续循环
```

以订单分析为例：

| 当前状态 | 下一步 | 为什么 |
| --- | --- | --- |
| “销售额”没有定义 | 请求确认指标和时间口径 | 直接查询会把假设藏起来 |
| 口径已确认但没有数据 | 查询本月与上月总额 | 先确认问题是否真实存在 |
| 总额下降，渠道字段可用 | 按渠道拆分 | 寻找变化集中在哪里 |
| 只有订单数据，没有流量数据 | 说明证据边界 | 不能把相关性写成因果 |
| 结果满足完成条件 | 返回口径、SQL 和结论 | 任务可以结束 |

“询问”“暂停”“转人工”和“停止重试”也都是合法决策。一个永远调用下一个工具的系统，通常没有清楚的完成条件。

## 模型、规则与工具怎样分工

第一版不需要把所有判断都交给模型：

| 工作 | 更合适的责任方 | 例子 |
| --- | --- | --- |
| 语义理解与候选步骤 | 模型辅助 | 识别用户是问趋势、排行还是明细 |
| 明确的业务规则 | 程序 | 日期范围、金额计算、状态枚举 |
| 外部数据访问 | 受控工具 | 执行只读 SQL、读取指标定义 |
| 权限、预算和终止 | 程序 | 账号权限、超时、调用次数 |
| 高后果判断 | 人或审批流程 | 是否发布报告、是否修改业务数据 |

一个实用的混合结构是：**模型提出动作，程序验证并执行。**模型请求执行 SQL 时，运行层可以检查语句是否只读、访问的表是否允许、是否有时间范围、是否超过资源限制；通过检查后才交给数据库执行。提示词里的限制不能替代数据库账户和接口层面的访问控制。

## 计划与决策不是一回事

计划是预先安排的路线，决策是当前一步的选择。最初计划可以是：

```text
确认指标 → 查询总额 → 按渠道拆分 → 输出分析
```

如果执行中数据库不可用，Agent 需要重新决定：有限次重试、使用已有结果、请求用户稍后再试，还是报告无法完成。预先写好的路线不能替代对执行结果的判断。

对于固定流程，代码编排往往更容易测试；只有在步骤确实需要根据上下文变化时，才让模型拥有更大的选择空间。扩大自主范围前，先问：错误能否被发现，操作能否恢复。

## 如何评价决策质量

准备一组包含正常、模糊、无数据和工具失败的任务，检查：

1. 是否理解任务和口径。
2. 是否选了合适的工具与参数。
3. 是否遵守权限和资源限制。
4. 结果是否与参考查询或业务系统一致。
5. 失败时是否说明原因，没有假装完成。
6. 没有进展时是否停止，而不是重复循环。

这能帮助区分失败来自理解、SQL、状态，还是回答阶段误读证据。不同原因需要改不同部分。

## 入门实现顺序

1. 先用程序固定“查询 → 校验 → 返回”的流程。
2. 只把“识别问题类型”和“选择查询模板”交给模型。
3. 为 SQL 增加只读校验、超时和结果行数限制。
4. 保存每一步的输入、工具结果和状态变化。
5. 用小型评价集观察错误，再决定是否需要更动态的循环。

## 一个练习问题

设计一个只读订单分析 Agent，回答“最近业绩怎么样”。在写代码前，先列出：需要确认的口径、可以调用的工具、不能执行的操作、完成条件，以及数据库超时时的处理方式。能够写清这五项，才算开始理解决策机制，而不是只会调用模型接口。
